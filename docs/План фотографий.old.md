Да, план такой: сначала надо разделить понятие “скачанный результат” на **video** и **photo album**, потому что сейчас весь проект завязан на один `VideoResult` с одним `path` и одним `telegram_file_id`. 

Важное ограничение сразу: **в обычном чате/группе можно отправить все фото альбомом**, но в **inline async-режиме нельзя заменить inline-сообщение на альбом из нескольких фото**. Telegram позволяет редактировать inline-сообщение в одно media-сообщение, но при inline edit нельзя загрузить новый файл напрямую — нужно использовать уже загруженный `file_id` или URL. ([Telegram][1]) А `sendMediaGroup` отправляет альбом из 2–10 элементов, но для него нужен `chat_id`, которого inline-бот после выбора результата не получает. ([docs.aiogram.dev][2])

## План добавления фото

### 1. Обновить модели в `app/models.py`

Сейчас есть только:

```python
VideoResult
```

Нужно заменить/расширить на универсальные модели:

```python
MediaKind = Literal["video", "photo_album"]

@dataclass
class MediaAsset:
    path: Path
    telegram_file_id: str | None = None
    media_type: str = "photo"  # photo/video

@dataclass
class DownloadResult:
    media_id: str
    kind: MediaKind
    source_url: str
    title: str | None = None
    assets: list[MediaAsset] = field(default_factory=list)
    from_cache: bool = False
    temp_dir: Path | None = None
```

Для видео `assets` будет содержать один файл. Для фото-поста TikTok — несколько картинок.

---

### 2. Переделать кэш в `app/cache_service.py`

Сейчас кэш хранит один путь и один `telegram_file_id` на видео.  Нужно сделать структуру вида:

```json
{
  "videos": {
    "7627161476968566047": {
      "kind": "photo_album",
      "source_url": "https://www.tiktok.com/...",
      "title": "...",
      "assets": [
        {
          "path": ".cache/7627161476968566047_001.jpg",
          "telegram_file_id": "..."
        },
        {
          "path": ".cache/7627161476968566047_002.jpg",
          "telegram_file_id": "..."
        }
      ],
      "created_at": 123456789
    }
  }
}
```

Функции `find_cached_by_url`, `find_cached_by_video_id`, `put_cache`, `update_cache_telegram_file_id` надо заменить на версии, которые работают со списком `assets`, а не с одним файлом.

---

### 3. Переделать `app/download_service.py`

Сейчас `download_service.py` всегда предполагает, что `yt-dlp` скачает один видеофайл и вернёт один `filepath`. Поэтому фото-посты ломаются. 

Нужно разделить логику:

```text
get_or_download_media(url)
├── probe_info_sync(url)
├── detect_media_kind(info)
├── если video → download_video_sync(...)
└── если photo_album → download_photo_album_sync(...)
```

Функция `detect_media_kind(info)` должна определять, что это фото-пост TikTok. Практически нужно посмотреть JSON от `yt-dlp --dump-json` на фото-посте и поддержать поля, где TikTok отдаёт картинки. Обычно стоит проверять несколько вариантов:

```python
info.get("entries")
info.get("images")
info.get("thumbnails")
```

После определения фото-поста нужно скачать все картинки в `.jpg/.webp` файлы, например:

```text
.cache/<tt_id>_001.jpg
.cache/<tt_id>_002.jpg
.cache/<tt_id>_003.jpg
```

При этом скачивание картинок должно использовать тот же `TIKTOK_PROXY`, что и `yt-dlp`.

---

### 4. Добавить отправку фотоальбома в `app/telegram_service.py`

Сейчас есть только `send_video_without_caption()`, которая отправляет одно видео через `answer_video`. 

Нужно добавить универсальную функцию:

```python
async def send_download_result(message: Message, result: DownloadResult) -> None:
    if result.kind == "video":
        await send_video_without_caption(...)
    elif result.kind == "photo_album":
        await send_photo_album(message, result)
```

Для фото:

```text
1 фото  → answer_photo(...)
2–10 фото → answer_media_group(...)
>10 фото → разбить на несколько альбомов по 10 фото
```

Telegram `sendMediaGroup` принимает массив из 2–10 медиа-элементов. ([docs.aiogram.dev][2])

Подпись должна быть только у последнего фото:

```text
Оригинал: https://www.tiktok.com/...
```

Например:

```python
caption = f"Original: {result.source_url}"
```

Если фото больше 10, подпись ставим только на последнее фото последнего альбома.

---

### 5. Обновить обычный handler в `app/handlers.py`

Сейчас `message_handler` вызывает:

```python
result = await get_or_download_video(url)
await send_video_without_caption(message, result)
```

То есть он работает только с видео. 

Нужно заменить на:

```python
result = await get_or_download_media(url)
await send_download_result(message, result)
```

Поведение останется прежним:

```text
Загрузка началась
→ скачивание видео или фото
→ удаление сообщения загрузки
→ отправка видео без подписи или фотоальбома с подписью
```

---

### 6. Inline async: выбрать реалистичное поведение

Для видео текущая async-схема нормальная:

```text
inline result
→ сообщение “Загрузка началась”
→ фоновая загрузка
→ editMessageMedia на готовое видео
```

Для фотоальбома так же сделать **полноценно нельзя**, потому что inline-сообщение можно заменить только на одно media-сообщение, не на media group. Поэтому существует единственный **правильный** вариант.

**Вариант D — несколько inline-результатов, по одному фото**

Бот может вернуть до 50 inline-результатов, например:
Photo 1
Photo 2
Photo 3
...

Telegram Bot API разрешает отвечать на inline query списком результатов, максимум 50.

---

### 7. Обновить `DUMP_CHAT_ID`-логику для фото

Для inline-видео `ensure_telegram_file_id()` загружает файл в `DUMP_CHAT_ID` и получает `file_id`. 

Для фото надо добавить аналог:

```python
async def ensure_photo_file_ids(bot: Bot, result: DownloadResult) -> DownloadResult:
```

Она должна:

```text
для каждого фото:
    если telegram_file_id уже есть → пропустить
    иначе отправить фото в DUMP_CHAT_ID
    сохранить полученный photo.file_id в cache
```

Для обычных сообщений это необязательно, но полезно для кэша: повторная отправка будет быстрее.

---

### 8. Обновить ограничения в `.env`

Добавить настройки:

```env
MAX_PHOTO_COUNT=35
MAX_PHOTO_SIZE_MB=10
PHOTO_ALBUM_CHUNK_SIZE=10
PHOTO_CAPTION_TEMPLATE=Original: {url}
```

`PHOTO_ALBUM_CHUNK_SIZE` лучше оставить `10`, потому что это максимум Telegram media group. ([docs.aiogram.dev][2])

## Итоговая архитектура

```text
app/models.py
├── MediaAsset
├── DownloadResult
└── PublicBotError

app/download_service.py
├── get_or_download_media()
├── detect_media_kind()
├── download_video_sync()
└── download_photo_album_sync()

app/cache_service.py
├── find_cached_by_url()
├── find_cached_by_media_id()
├── put_cache()
└── update_cache_asset_file_id()

app/telegram_service.py
├── send_download_result()
├── send_video_without_caption()
├── send_photo_album()
├── ensure_telegram_file_id()
└── ensure_photo_file_ids()

app/handlers.py
├── message_handler → supports video/photo album
├── inline_query_handler → video async + photo fallback
└── chosen_inline_result_handler → async video, limited photo support
```

Главный технический вывод: **обычные сообщения можно сделать идеально: все фото одним альбомом с подписью-ссылкой. Inline async для фотоальбомов полноценно невозможен из-за ограничений Telegram API, поэтому там нужен fallback.**
